# Vanilla 防御与可选 RTS 指挥

[架构说明](architecture.md) · [English](../en/combat-architecture.md)

Vanilla 提供日常敌意、自卫、逃跑、绘制巡逻路线、有限补给和真实近战／弓／弩会话。可选 `folkways_rts` 负责直接指挥居民及对应服务端／客户端交互。本次只调整模块归属，保留已接受的命令和输入语义；Superb Warfare 与 TACZ 可选集成见下文；可选 `folkways_raid` 通过 Vanilla 防御增加殖民地袭击；战略 AI 仍未实现。

## 模块边界

| 模块         | 职责                                                                                                                                                                                                                                                                               |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Core         | 居民、劳动、物品所有权、生命周期、通用出行、控制保留与互斥执行；通用书页、俯视工具和个人相机 API                                                                                                                                                                                   |
| Vanilla      | `plugins.combat` 下的 NativeHostility、Threats、CombatTags、武器、LoadoutRegistry／LoadoutProvider、PatrolSupplies／PatrolSupplyNode；`plugins.patrol` 下的 Beats、Wards、WatchNode、PatrolPresence、StrikeNode 及原有绘制巡逻职业；清醒计时与防御所需 mixin                       |
| RTS          | `rts.combat.command` 下的 ResidentCommands、CommandNode、AttackNode、CommandContent；`rts.combat.group` 下的 UnitGroup、UnitGroups、Deployment、PointRoute 与编队；`rts.combat.control`、`net`、`ui`；`rts.client` 下的 CombatController、CombatProjection、CombatCards、RtsClient |
| 独立枪械扩展 | Warfare 通过 Vanilla 武器／档案／武器站契约执行 SBW；`mods/tacz` 通过配置与武器会话执行 TACZ；Point Blank 仍为后续工作                                                                                                                                                             |

`mods/rts` 通过 `FolkwaysRtsMod` 注册 `folkways_rts`，客户端和服务端均依赖 Vanilla 与 Core；Vanilla、Core 不依赖 RTS。Create、Cookery、Modular Golems 保持独立扩展。

Vanilla 的小型 `DefenseControl` 服务 API 只观察当前手动命令、选区保留和失败待命；未安装 RTS 时返回空观察。RTS 通过既有聚落服务扩展提供 `CommandDefenseControl`，守卫暴露原有命令对象、目的地、仅自卫标志和交战回调。保留对象身份，使改令仍会撤销旧补给行程。守卫约束范围、受伤恐惧优先级及反击规则不变；失败待命不能恢复旧巡逻主动索敌或补给，生活服务仍按这些观察推迟受控睡眠。

整个 `folkways:combat` 战斗页、desk、俯视工具及战斗报文注册均归 RTS。仅安装 Vanilla 时不再提供基于 UnitGroup 的单点站岗及两点巡逻书页，原有绘制巡逻路线保持可用。RTS 为自身小队和命令注册原有页面，只显示居民配装名称；Vanilla 另行注册 `folkways:loadouts` 配装页，负责编辑与分配；巡逻同时拥有下文的绘制哨位。Loadout 共用标签保留在 Vanilla API，战斗页与 RTS 文案移入 RTS 的四种语言文件。除输入／状态命名空间改为 `folkways.rts.*` 外，既有翻译键保持稳定。

### 存档与协议兼容

聚落账本 owner `folkways:unit_groups`、队伍 UUID 及有序 `groups`／`members` 格式不变，RTS 直接读取既有数据，不做破坏性转换。Core 在 RTS 缺席时保留未知 owner 数据，所以只装 Vanilla 保存世界不会丢弃队伍成员；重新安装 RTS 后，仍在名册中的成员以 IDLE 恢复。命令、部署、路线、选区、快捷组和运行句柄仍是临时状态，不从存档恢复执行。`folkways:patrol_loadouts` 及既有装备偏好迁移继续由 Vanilla 管理。

RTS 在自身 mod bus 注册报文，报文 ID 与专用版本 6 registrar 保持不变，客户端／服务端需同时满足模组依赖及协议匹配要求。Vanilla 单独运行不注册战斗报文。

### 本次重构设计审计

独立 `rts_design_auditor` 已按现有输入和生命周期契约完成终审，通过本次模块归属调整的静态设计审查。接受范围为模块拆分、可选的空防御观察、RTS 内保留原战斗页、存档 owner 不变及测试迁移。验收覆盖 Vanilla 独立敌意／绘制巡逻／有限补给、守卫改令撤销补给、失败待命与有界自卫、受控睡眠、挂起／输入租约和失权清理、精确快捷组引用并集、拒绝命令快照及旧存档往返。修饰键所有权、服务器权威、可见失败原因和完成规则按下文原契约保留。静态审计与工程测试、真实客户端玩法验收分别报告。

移动射击、维护、显式休整、战略 AI、快捷组持久化和规模扩展继续留待后续。

## P0/P1：日常敌对与防御

`NativeHostility` 在服务端 EntityJoinLevelEvent 中只安装轻量 Goal，不查询世界。实际索敌延后到正常 AI tick，避免区块尚未 FULL 时查询世界。

- 为实现原版 Enemy 接口的怪物安装一个轻量居民目标；只有进入实体类型标签 `folkways:resident_enemies` 的类型才执行索敌。优先级不早于 6，且排在安装时的所有原生目标之后。移动、近战、射箭和苦力怕引爆继续由怪物原生 AI 执行。
- 排除 NeutralMob，避免继承 Zombie 的僵尸猪灵变成主动敌人；末影人保持原版中立语义。
- 通过 Bodies.of 和聚落身份筛选居民，兼容其他注册 ResidentKind。离籍、死亡和移除会结束追击。
- 重复进入不累加 Goal；NBT 重载的新实体重新安装。测试包含自动发现、实际追击和伤害、两类怪物重载，以及原版村民目标。
- Threats.hostile 供巡逻和实际打击共用，尊重同盟与中立怪物的当前愤怒状态。出手时再检查敌对资格和视线。
- 默认名单含僵尸和骷髅的原版变种、蜘蛛、洞穴蜘蛛与苦力怕。蜘蛛仅在原版亮度值低于 0.5 时主动索敌；明亮处未交战的蜘蛛也不被巡逻主动挑衅，已发生的战斗按原版攻击 Goal 脱离。
- 武装居民离岗后可反击 100 tick 内、12 格以内的怪物袭击者。生命不高于 35% 时，恐惧高于反击；巡逻继续复用 StrikeNode。
- 无武装居民沿用伤害或火焰触发的恐惧；袭击者仍在追赶时继续避险。安全点采用有用的距离增益，逃跑目标保持到抵达、失败或 120 tick 截止，避免随机采样为空时反复撤回。

### 可继承的敌意标签

1.21.1 的原版 `Enemy` 是 Java 标记接口，NeoForge 的通用实体标签没有提供等价的完整敌意名单。巡逻保留对 Enemy 实现的自动识别，数据包可使用以下实体类型标签补充或排除。

| 标签                                | 用途                                                             |
| ----------------------------------- | ---------------------------------------------------------------- |
| `folkways:resident_enemies`         | 允许已有原生攻击 AI 的 Enemy 类型主动索敌聚落居民                |
| `folkways:undead_resident_enemies`  | 被上一个标签引用的原版僵尸、骷髅变种名单                         |
| `folkways:patrol_targets`           | 巡逻的额外候选；默认继承 resident_enemies，已有 Enemy 仍自动识别 |
| `folkways:ignored_resident_enemies` | 优先排除 Folkways 附加索敌和巡逻主动攻击                         |

例如在数据包 `data/folkways/tags/entity_type/resident_enemies.json` 中追加自己的分类：

```json
{
  "values": [
    "#my_pack:hostile_undead",
    { "id": "my_mod:monster", "required": false }
  ]
}
```

标签可以嵌套引用，`replace: true` 可替换既有名单。每次尝试索敌及继续追踪均读取当前标签，`/reload` 对已加载实体生效，不额外叠加 Goal。中立状态、聚落居民身份与同盟检查仍然生效。标签不会补出没有的原生攻击动作；排除名单也不关闭原版反击或已经开始的苦力怕引线。

## P2：单居民命令与返岗

公共 API 位于 RTS 的 `rts.combat.command.ResidentCommands`：

```java
var commands = ResidentCommands.of(colony);
var order = commands.hold(body, destination);
order.close();
```

| API         | 行为                                          |
| ----------- | --------------------------------------------- |
| move        | 到达后标记 ARRIVED，自动交还劳动控制          |
| hold        | 到达后驻守，等待解除；可指定朝向              |
| retreat     | 以更高优先级及 1.3 倍行进速度撤退，到达后驻守 |
| guard       | 保留阵位，允许战斗和恐惧安全抢占，结束后回位  |
| Order.close | 只解除该句柄，旧句柄不能取消新命令            |
| current     | 查询当前命令和 MOVING、HOLDING 等状态         |
| validate    | 只验证，不接管，供小队整批校验                |

API 要求可信服务端线程、真实聚落登记、已加载且未乘坐载具的 PersonBody，以及同 realm 内 128 格以内的已加载目标。战斗页在每次服务端操作时重新确认当前聚落管理权限，并在调用 API 前验证成员归属与目标范围。其他 ResidentKind 的命令支持需要单独验证。

命令复用 Core 现有 Urge → ColonyLabor → BodyRunner 安全中断流程。旧任务释放展示工具和出行后，同一个执行器开始命令；没有第二个导航控制器。解除后执行最新计划，不重放已撤销任务。Core 仅补充过期临时 Urge 拒绝记录回收，以及通用 `Node.directTravel()` 选项。该选项使用居民现有 Locomotion 走本地路径；普通劳动仍采用原有多方式出行规划。

命令不持久化。死亡、卸载、离籍和聚落关闭会释放控制；移动超过 1200 tick 也释放并标记 FAILED。驻守和已到达的撤退等待显式解除，期间可能压制日常需求。通过通用 `Node.staysAtWorkSite()` 约束，居民受推离开后由同一执行器重新回位。失败或旧存档句柄不代表有效控制权。

GUARD 让出同一执行器给恐惧或战斗时，不消耗移动计时；实际重新取得执行器后继续计时。从未取得执行器的命令仍保留有限等待上限。

## P3：实际 UnitGroup 与部署意图

`UnitGroups.of(colony).create(people)` 创建实际队伍，`ofResident(id)` 查询唯一归属。实际成员及存档加载不再截断为 8 人。转组解除旧队伍对该成员的控制。队伍 ID、成员顺序写入聚落账本；部署命令不持久化，重启后队伍恢复为 IDLE。

```java
var group = UnitGroups.of(colony).create(people);
group.move(new Deployment(left, right, front, new Deployment.Formation(2)));
```

Deployment 接收两个同高度、同 realm 的端点、与阵线近乎垂直的水平正面方向，以及 2～8 格间距。`Formation(spacing)` 保留单排横队；`Formation(spacing, columns)` 支持指定列数的多排阵位。端点线长仍不超过 128 格，各成员必须具有不同且安全的整数阵位。RTS 提交部署意图，无须逐 tick 操纵居民。

- move 按顺序让成员进入目标纵队，再恢复横队，避免后排先占位堵住前导成员。纵队阵位无站立空间时尝试直接横队。
- hold 直接建立横队；gather 在中心附近集合；release 解除全部成员命令。
- guard 建立可被战斗和恐惧安全抢占的站岗编队，使用真实 GUARD 命令并沿用队伍生命周期。
- retreat 通过实际队伍维护高优先级撤退命令，到达后驻守；其他有权管理聚落的玩家也可从战斗页解除，旧队伍句柄不能覆盖成员后来收到的个人命令。
- 单人新命令或单人解除会让该成员退出队伍控制，旧队伍不会覆盖新句柄。
- 死亡、离籍成员移出；卸载成员保留为 missing，现有成员重排；重新加载后分配新阵位。
- 无路可走时报告 FAILED 并释放全部成员，可在开路后重新提交。没有强制传送或无限重试。

四人单格开口与恢复横队是已验收的具体场景。新增紧凑多排尚需游戏实测，不保证所有瓶颈、任意地形、载具或舰船部署；单独的 16/32/64 总实体战斗采样不能推广为大编队性能保证。RTS 的快捷选择集可以重叠，实际队伍归属不能重叠。

临时纵列阵位可以在预定高度上下两格内寻找安全落脚点，最终横队仍要求精确站位。高度调整后的临时阵位不可达时，重新验证并尝试最终横队一次；最终横队仍不可达就失败释放。另有四人通过两次单格转弯及两级台阶、再返回巡逻的验收场景。

### 编队巡逻与主动交战

`group.patrol(List<Deployment>)` 接受 2～16 个同 realm 的部署点，循环执行纵列入场与横队重组。`patrolRoute()`、`patrolStop()` 和 `phase()` 提供观察；路线及交战状态不写入存档。

- GUARD 的权重为 1.5，健康交战为 2.5，恐惧为 2，显式撤退为 4。仍由同一 BodyRunner 交接，不增加战斗导航控制器。
- 携带可用武器的守卫无需先受伤即索敌；目标与交战阵位均限制在当前守卫槽 12 格内，避免无界追击。远程武器在有视线及射程内优先原地射击。
- 健康守卫短期续交战租约，队伍显示 ENGAGING、暂停路线与移动超时。低血战斗不续租，恐惧可以接管。
- 敌情解除后先返回本次阵位，现有成员全部归队并停留 20 tick 后再去下一站。死亡、失联、回归与单人撤退沿用真实队伍的成员处理。
- 队伍的 HOLDING 与停留计时同时检查实际成员位置；GUARD 被抢占后先回到 MOVING，不能用交战前缓存的到岗状态提前推进路线。近战站位预留导航到站容差，实际伤害仍检查原生距离和视线。
- 所有路线点先验证，再替换现有控制。不可达时 FAILED 并释放；全员失联时保留临时路线并 WAITING，重载后从当前站重新组队。

### 战斗页与点位配置

RTS 通过既有 Front 扩展接口，在殖民书注册独立 `folkways:combat` 战斗页。页面可以选择已加载居民、创建或选择实际队伍，从玩家脚下或服务端验证的瞄准支撑面添加点位，再显式执行。一个点配置站岗点，两个至十六个点配置循环巡逻；每个点是阵型中心，不是部署线的一端。

页面同时提供撤退、解除及配装名称（编辑与分配移至 Vanilla 配装页）。每次操作在服务端重验管理权限；失效或其他聚落的队伍 ID、部署时失联的成员、无效地形和越界目的地均不能接管控制。含卸载成员的队伍仍可解除。点位草稿保留在当前服务端会话中，重启不会恢复运行命令。RTS 同时注册下文的俯视选择输入。

### V 入口与个人相机设置

Core 提供 `RegisteringUi.tool(OverheadTools.Tool)`，供扩展声明独立的俯视工具、图标、相机偏好及开页动作。RTS 注册 `folkways:combat`，与点选、圈地、画线并列。未安装 RTS 时不提供此工具和页面；安装后世界区域的左右键用于下述战斗操作，“队伍与命令”仍可打开站岗、撤退、解除和补给设置。关闭 V、切工具或收起书只挂起交互；已接受的实际小队及任务继续，不要求先绑定数字快捷组。无任务、无快捷组的纯临时选择可以释放。

默认只有战斗工具使用新操作：中键拖动在水平面平移，Alt＋中键围绕视线焦点等距旋转。焦点由中心射线的实际碰撞确定，没有有效地面时使用有限距离回退；一次拖动锁定操作及焦点，中途改变 Alt 不切换手势。平移维持世界高度，当前未实现地形高度跟随或建筑避障。其他工具在默认设置下保留原有相机和修饰键行为。

书内设置和 NeoForge 模组配置页均提供“全局战斗视角操作逻辑”，开启后全部 V 工具采用新操作。可自定义快捷键控制同一选项，默认不绑定，输入文字时不触发。该选项注册于 `folkways_core` 的 CLIENT 配置，保存在本地 `config/folkways_core-client.toml` 的 `book.globalTacticalControlUsers`，按启动账号 UUID 分别记录；不写入殖民地、世界或服务器配置。未列出的账号默认关闭，切换聚落不会改变偏好。

`Pages.open(page)` 通过客户端桥请求声明的主书页，服务端重新检查手持书、当前聚落及管理权限，并拒绝未知或隐藏页面。`Overhead.camera()` 仅提供客户端相机观测，不增加居民控制权或命令执行入口。

### RTS：屏幕框选、快捷编队与鼠标命令

Core 提供通用 OverheadTools.Handler 和 Overhead.screenRay()；可选 folkways_rts 同时负责 CombatPackets、SelectionOrders、CombatSelectionOwnership、UnitGroups 及输入显示。实际命令继续通过 Core 原有 BodyRunner 和移动能力执行。

| 操作           | 结果                                                         |
| -------------- | ------------------------------------------------------------ |
| 左键拖动／单击 | 用当前聚落可用居民替换可见选区                               |
| Shift＋左键    | 框选追加成员；单击切换该成员是否选中；按下鼠标时锁存增选意图 |
| Ctrl＋1～9     | 用精确选区替换该快捷组；与原组完全相同时解散该组并保留选区   |
| 1～9           | 选回服务端当前保存的快捷组；支持主键盘和小键盘数字           |
| G              | 切换持续移动／攻击移动模式，无需选择、不发送命令             |
| 右键地面       | 按当前移动模式替换路线，以点击处为逻辑队长目的地             |
| 右键非友方生物 | 下达原生明确攻击；不包含居民、友方或玩家                     |
| Ctrl＋右键     | 每点击立即执行或追加一个必经点；重访旧点形成循环巡逻         |
| Esc／空地左键  | 清除可见选区；已无选区时 Esc 可退出俯视界面                  |

快捷组可以重叠；同一居民同时只由一个玩家持有，只执行一套实际小队命令。RTS 在服务端保存每玩家选区和九个快捷组。居民只要仍在选区或任意快捷组中，就不参与普通劳动分派。每名居民单独按引用并集判断：ABC 改成 AB 后，C 没有其他引用才释放；同集合 Ctrl＋1 只清快捷组，ABC 仍被框选，不能返岗。

选择指针手势通过 Handler.blocksCameraDescent() 暂停相机下降；Shift 增选意图在左键按下时锁存，提前松开 Shift 不会把追加变成替换。未进行选择手势时，纯 Shift 仍使相机下降；中键平移与 Alt＋中键旋转保留原有手势所有权。

Core 的被动 Urge.reserve 从劳动调查中移除受控居民，并通过原 BodyRunner 正常收尾已有普通图劳动，工具材料沿原结算流程归还。保留本身不创建目的地、队形或导航所有者；生理、恐惧和自主战斗仍可使用同一个执行器。RTS 仅跟踪该控制会话实际发出的小队命令 generation，覆盖移动、攻击、停止及其重组待命；最后引用移除时释放对应旧控制，不取消后来的替换命令或书页部署。

界面挂起与普通取消选择是不同操作：SUSPEND 只保留当前会话仍拥有实际队伍及命令 generation 的原选择引用和九个快捷组；未确认、未发送的追加输入不在重开时重发。普通 Esc／空地清选、Ctrl 精确改组及显式解除仍按原逐居民引用并集结算；不新增会吞掉“ABC→AB 释放 C”规则的永久任务引用。重开后以服务端快照恢复同一小队、命令进度和快捷组。

新选择和新命令仍要求持书、当前聚落与真实管理权限；已接受任务续行依据在线玩家的真实聚落权限及既有 level／realm 边界，不因换手或开关 V 失效。100 tick 仅是临时输入租约，到期执行同样的挂起修剪，不撤销有效任务或快捷组；客户端可以继续每 40 tick 后台心跳，但任务不依赖它续命。失权、切当前聚落、跨 realm、断线、死亡和实体卸载仍安全清理。本轮不增加离线执行、跨世界调兵或存档后恢复运行句柄；快捷组尚未持久化。

Ctrl 每个点击都立即下达。A→B→C→D→B 先经过 A，再循环 B→C→D→B。开放路线到末点后，全队集合并停留 20 tick，继续受控等待；之后追加不会重走前缀或重复已完成的停留。仍有效的普通单点 A 可用 Ctrl 点 B 扩成队列。闭环后的编辑暂时冻结，继续 Ctrl 点击会明确提示先用右键重设路线；普通右键始终替换整个旧路线。

路径标记仅来自服务端已接受快照。重新框选、恢复界面或召回快捷组会恢复对应完整实际小队的路线；替换命令被拒绝时保留并返回旧路线。控制操作和移动命令具有单调请求序号，客户端丢弃旧回复；战斗专用网络协议为版本 6，客户端与服务端必须一致。进度观察包含命令 generation、当前停点、完成状态及待归队人数，客户端只把匹配 generation 的进度应用于已确认路线。

PointRoute 不生成额外队长实体。第九批把途中凝聚与到站集合分开：从同一真实参考居民及导航实时游标截取累计最多 6 格的可用路径前缀，允许有用的部分路径；参考居民距进度锚点两格、其他成员距各自站位三格以内即可继续行进。到达玩家指定点时，仍要求参考成员经过该点、全员进入既有 Reach 容差并持续停留 20 tick。每路段最多 2400 个有效行军 tick，交战、恐惧、全队未加载和到站驻留不消耗预算。

站位沿用成员相对偏移，检查真实体积不重叠；只在规划或恢复批次探测可达性，每成员最多 12 个候选。短暂无路跨 tick 重试三批，分别退避 10／20 tick。成员连续 100 个有效 tick 未改善至少半格时，最多尝试两次重寻／换槽。耗尽后保控等待，分别报告无路、成员受阻或行军超时及待归队人数，不跳过必经点、传送或自动返岗。这仍是有界恢复，未宣称通用窄路可靠性或大规模寻路性能已经验证。

Core 的 `Urge.Priority.CONTROL` 将玩家控制与普通需求的数值权重分开，移动、驻守、撤退与明确攻击不再排在劳动或高权重个人需求之后。仍由同一 BodyRunner 安全交接，原工具及材料沿原流程结算。新点巡逻的到站 GUARD 以 `Order.deliberateGuard()` 保持控制优先，实际交战或低血遇险时才借出执行器；旧自主 guard 规则不变。扩展的真实硬直或生命周期锁仍然有效。

左侧输入提示通过 `Handler.cues()` 显示当前工具的实际操作，战斗下不再显示登记／移出、打开书页或旧旋转说明。`bottomInset()` 为底部兵牌预留空间，提示从顶部按钮下方排布。底部显示 1～9 编队卡和当前选中居民的头像、血条及分页；点击编队卡选回，Ctrl＋点击保存，数字键对应相同操作。头像使用居民外观声明的皮肤或模型回退皮肤，不重复渲染每个三维实体。Tab 按“点选→圈地→画线→扩展工具→点选”循环，切换时清除未完成的图形草稿。

明确攻击通过同一执行器接近目标并使用真实 `WeaponSession`，持续重验指挥者权限、目标身份、友方关系、距离与生存状态；600 tick、起点 64 格及指挥者／居民距目标 128 格的边界限制追击。`WeaponSession.explicitTarget(target, authorized)` 为扩展提供单目标、实时可撤回的授权，默认拒绝；扩展必须明确实现，不能将一次许可推广到其他目标。原版中立及巡逻自主索敌规则不变。本增量不开放玩家 PvP。

客户端居民身份通过服务端按当前持书权限返回的名单确认，不读取未同步的 Body 附件猜测归属。命令包含明确的聚落 ID、居民 UUID 和 WorldPos。服务端重新检查所有成员、全部路线点及最终阵位后才接管；无效命令不会部分迁移成员。选中者可以来自多个实际队伍，未选者保留原队伍与命令意图，旧句柄不能取消新命令。一次提交的安全上限为 256 人、16 个路线点，超限整次拒绝，绝不截取前 8 人；这不是 256 人性能或复杂地形通过保证。

本轮快速迭代先编译全部模组与 GameTest 源码，再替换日常实例供人工测试。编队、控制权、攻击收尾、失败待命和战后续路的 GameTest 源码必须区分“已编译”与“已运行”。更新 PR 前再运行 GameTests 与 Blockwright，覆盖屏幕框选、快捷键冲突、闭环路径、窄路、死亡／卸载和存档重载。

### RTS 设计审计与下一阶段

后续涉及 RTS 操作、命令语义、选区、快捷组、编队、队列或战斗界面的设计改动，先交独立 RTS 设计专家审计；本对话复用 rts_design_auditor，其他会话恢复同一专家角色。审计记录规则、输入冲突、服务器权威、结束条件和验收场景；设计审查与工程验证分别报告。

第八批落实以下已审规则；静态设计通过不代表运行时验收：

- 完整选中同一实际小队时，指定攻击保留小队 ID；部分或跨队选区建立一个新小队，未选成员保留旧意图。新攻击替换旧路线。目标死亡、消失、失去敌意、越界或超时后结束追击，在幸存者附近重组，全部到位且无交战／恐惧借用达 20 tick 后驻守待命。
- 目标离场事件与逐 tick 检查共用结束分类：生命归零或 KILLED 为 TARGET_DEFEATED；健康目标被丢弃、卸载或转移为 TARGET_LOST。两者仍按原规则重组，旧句柄不能取消新命令。新地面路线可以替换实际小队；完整小队 STOP 和既有路线追加保留对应的小队身份。
- 重组无安全锚点、成员执行失败或有效移动耗尽 1200 tick 时进入 FAILED_WAITING，保留控制和可读原因，不再追击、推进路线或恢复旧巡逻主动索敌／补给。仍允许真实攻击者触发的有限自卫及恐惧。没有幸存者不得报告成功；新命令可以立即替换等待。
- G 持续切换本地移动／攻击移动输入偏好，右键地面提交对应策略，左键始终选择。接受、拒绝与清选不消费模式。每条路线固定策略；Ctrl 追加必须双向匹配当前偏好，包括待确认替换。不同模式显示失败且保留路线，普通右键建立新路线。在途输入捕获提交时策略，不被之后 G 改写；不画未确认标记。离开 RTS 输入屏幕或玩家／殖民地／领域变化恢复移动，已接受任务继续。
- 攻击前进只自动迎击既有敌意生物，目标和可达战位受战前阵位 12 格范围约束。交战保持逻辑队长及当前未完成路径点，结束后回原阵位稳定 20 tick，再继续路线；指定路径点仍必须经过并停留 20 tick。普通地面移动继续优先赶路。
- “停止”立即取消路线和追击，在附近重组并保留控制，只作有限自卫；没有安全锚点也接受停止并显示失败待命。“解除控制”在服务端原子移除所选居民在当前选择及全部九个快捷组中的引用，再释放本会话控制，未选成员不变。
- 底部状态条显示服务端确认的当前命令、行进／交战／重组／等待和结束原因。停止与解除均等待实际确认；状态标识在客户端翻译。保留中键平移、Alt＋中键旋转及现有个人设置，不占用 WASD、Shift 或 Tab 新快捷键。

第九批根据实机反馈补齐以下规则；这些变化仍需人工与 PR 前运行时回归：

- 普通右键移动和点队列都从当前队伍观察中心画向正在执行的目标，显示剩余命令意图，不冒充实际导航绕行路径。已执行前缀隐藏；循环保留循环段。开放末点完成全员到站及 20 tick 驻留后隐藏完成线，但服务端历史、控制权和继续 Ctrl 追加／闭环能力保留。按住 Ctrl 时可临时回看已确认历史的淡色标记来闭环，松开恢复剩余段；只有实际显示的已确认标记参与像素吸附，未确认输入不画草稿也不作不可见吸附。
- 下方紧凑布局将底栏恢复为 60 个界面单位；九个快捷组、命令快捷键及执行失败原因仍可访问。左侧只常驻核心提示，其余放悬停帮助；其他工具保留旧提示。选中世界居民只显示轻量短血条，每帧仅投影一个头顶点；框选命中投影在输入事件中计算，拖动只绘制一个选择矩形。未测量实际 FPS，不把截图中的卡顿归因于单一绘制步骤。
- 选区、任意快捷组引用或有效手动命令均推迟睡眠，包括失败待命；撤下睡眠 Urge 使原执行器安全结束已有躺卧。最后控制引用和手动命令解除后恢复睡眠，恐惧、战斗与进食仍保留其原规则。
- Vanilla 时间疲劳改为所有已加载居民的实际清醒时钟，普通闲站也会疲倦；每 30 tick 增加一点基础疲劳，一 MC 天达到原困倦阈值 800，并受 FATIGUE 效果调整。劳动结算不再重复计 activeTicks 的时间疲劳，实际步行距离和原饥饿耗能照旧。睡眠、缺失 tick、离线及重载首个观察不补扣；旧 Tired 数值存档继续兼容。休息不足仍沿用心情 −5／−10，没有第二层熬夜数值惩罚。

第十批的挂起／续行契约通过独立 RTS 静态终审。客户端暂未追踪到居民只能影响绘制与命中，不能自动缩小服务端选择；无新命令在途时，权威心跳也可恢复路线，避免挂起回复被后续心跳覆盖后丢失显示。新 GameTest 和 E2E 源码覆盖不绑数字组续行、输入租约、收书及重开时的追踪缺口；本轮只编译检查，实机往返及网络时序验收仍待执行。

后续继续验证窄路、台阶、重组与实际掉队恢复，再推进完整兵牌、持久化和规模性能。先验证 16～32 名居民加对等敌人，256 仅是报文安全上限。个人相机设置和非战斗工具操作保持原契约。

### 行进作战与脱战维护设计（已审方向，尚未实施部分）

本轮实现界面挂起及持续授权修复；下面的移动射击和维护协调是下一阶段设计，不表示已有对应新按钮、武器能力或运行验证。

| 意图         | 规则                                                           | 接敌或结束后的行为                                           |
| ------------ | -------------------------------------------------------------- | ------------------------------------------------------------ |
| 直接移动     | 右键地面，优先到达指定点，不主动偏离路线猎敌                   | 到站保持控制，必要时有限自卫                                 |
| 行进迎敌     | 现有攻击前进：沿途发现既有敌意生物后停步、有限接敌             | 回战前阵位，重组后继续未完成必经点，不重走前缀、不跳点       |
| 真正行进攻击 | 计划按武器会话声明的移动能力，协调同一执行器内的移动与原生攻击 | 目标、视线、射程、敌意或能力失效立即停火，路线保留           |
| 脱战维护     | 计划在约 100 个连续游戏刻无有效交战、开火或新伤害后允许维护    | 维护不改变玩家任务；新命令立即中断并正常收尾                 |
| 显式休整     | 计划提供明确的暂停任务／允许休息意图                           | 保留小队控制与待续路线，不把休整当作返岗；恢复时重建执行资源 |

真正行进攻击必须沿用同一个 BodyRunner 和独占 WeaponSession，不另开后台攻击 Goal、第二个导航者或第二份持械物品。近战只在真实触及范围攻击，不能以“行进攻击”为由无限脱队追杀。弓保留真实蓄力、弹药和耐久；弩保留真实装填与已装弹组件。移动速度、转身及可射击窗口由实际武器／会话能力决定，未声明者默认停步。未来可在 WeaponAdapter／WeaponSession 增加明确的移动使用能力；该接口仍为设计，未为 TaCZ、Point Blank 或其他未实现武器写兼容桩。Epic Fight 动作也必须实际验证后才开放对应移动窗口。

脱战是观察到的战斗条件，不是自动替换玩家命令的新命令。维护优先限于最终待命、驻守或停止状态；巡逻停点是否允许延长驻留应显式配置，不能每次接敌后自动改道或跳过路径点。计划先支持原地吃实际携带食物，再考虑既有有限补给；缺粮、缺箭、缺床和无法维护应分别可见。

- **生命**：已有 Hunger.stepVitals 继续遵守 naturalRegeneration、食物与饱和度。不增加“脱战立即回满”，也不趁此修改现有自然回血在战斗中是否允许发生。
- **食物**：计划维护窗口只借用同一执行器吃实际携带的一份食物，完成后回原待命任务；不默认绕去远处餐桌或制造食物，新命令优先。
- **疲劳与心情**：清醒脱战仍会疲劳，脱战不清空受击心情历史或重置休息债务。受控睡眠仍须后续显式休整授权；休整暂停整个小队路线，不以缺员方式跳过必经点。无可用床时显示缺床，不伪造免费睡眠。
- **箭与装备**：复用真实库存、登记仓库访问规则、已有数量与距离上限及超时；不凭空补箭、修耐久或覆盖玩家装备。新命令撤销维护，真实借用物沿原结算路径归还。
- **状态**：计划把当前命令、战斗条件和维护状态分开显示，例如“巡逻／脱战观察”“驻守／进食”“攻击前进／缺箭”；60 单位底栏保留短状态，详情按需显示。

后续顺序为：验证本轮界面外任务续行 → 完善现有行进迎敌 → 有界脱战维护 → 显式休整 → 原版远程移动射击。验收覆盖不绑数字组退出 V、收书超过 100 tick、重开同一 generation、普通清选／精确改组／失权清理；随后验证接敌不跳点、游戏规则禁回血、真实食物箭耗、维护改令、休整恢复以及单一导航和武器所有权。仍不开发战略 AI、PvP、RTS 框架迁移或枪械模块。

## P4：实际原版武器会话

`plugins.combat.weapon` 公开 `WeaponAdapter`、`WeaponSession` 和 `Weapons`。`Weapons.register(id, adapter)` 在模组初始化时注册独立适配器、拒绝重复 ID；默认提供真实近战、弓和弩实现，没有枪械桩。

| API／状态                | 实际行为                                                                          |
| ------------------------ | --------------------------------------------------------------------------------- |
| accepts／usable／range   | 识别物品、真实弹药或已装填弩，以及有效射程；无弹远程武器可退选库存中的剑          |
| open                     | 从真实 Pack 移出唯一物品到独占主手，不复制装备；由当前劳动节点取得并推进          |
| READY／FIRING／RELOADING | tick 驱动近战挥击、拉弓、弩原生装填与发射，每次执行检查敌意、视线、距离与生命周期 |
| stop／STOPPING           | 终止新射击、清除蓄力；原版停止无需异步等待，不调用会误射箭的 releaseUsingItem     |
| close／CLOSED            | 幂等归还真实装备；背包满时仅掉落一次                                              |

工作展示副本与真实主手会话分开管理。弓复用原版 ProjectileWeaponItem 的 draw/shoot；弩复用原生 releaseUsing/performShooting，真实消耗箭、保存装填组件与修改耐久。Native 会话的 stop 是终止操作，继续射击须取得新会话；已发出的投射物继续按原版飞行。

Entity 在 addAdditionalSaveData 前序列化附件，因此 ResidentEntity 在 saveWithoutId 入口先停止并归还武器，保证 Pack 快照仅拥有一份。卸载、离籍、死亡及聚落撤销均终止会话；弩已装弹组件随真实物品保存。

原生持械会话目前支持 ResidentEntity。其他 ResidentKind 保留原有 ToolUse 近战及已声明的裸手战斗，不因携带剑或弓而失去原有攻击；真实持械会话需所属扩展接入。TaCZ、Point Blank 与异步持续枪械动作仍需各模块实际适配与验证。衣甲仍由 Core Equipment 管理。

### 聚落配装

`LoadoutProfiles.of(colony)` 管理多份不可变 `LoadoutProfile`：UUID、可编辑名称、有序 `Entry` 及可选旧偏好数据。条目各有 UUID、`WEAPON`／`ARMOR`／`SUPPLY` 类别和支持组件约束的 `ItemSpec`。每条武器或护甲各需一件实物；护甲指定头、胸、腿、脚栏位。补给保存玩家设置的目标及阈值，范围为 `0 <= threshold <= target <= 4096`。重复或重叠条目分别占用真实数量；组件匹配贯穿库存预览、领取、结算、装弹计数、缺额及背包保留。

沿用聚落账本 owner `folkways:patrol_loadouts`，新格式为 `version: 4`、`profiles`、`assignments`。配装保存 `id`、`name`、`entries` 和可选 `legacy`（`loadout`、`options`）；条目保存 `id`、`kind`、`items`、可选 `slot`、`target`、`threshold`；分配记录保存 `resident`、`profile`。未加载居民保留分配；离籍只移除分配，不删除可复用配装。删除配装取消所有相关分配；复制配装只复制条目，不复制居民名单。

第一版枚举名及第二版 `Selection` 标识／选项仅迁移一次，相同偏好合并为同一配装。原版弓弩迁移为武器与箭条目，目标八支、阈值八支，保留原先低于八支补充的行为。未安装扩展的原始标识与选项保留在已分配但显示不可用的配装中，重命名、复制及反复保存均不丢失。缺少组件编解码器的 ItemSpec 原样保留为不可用条目，重命名、复制、保存均不丢失，编解码器恢复后重新解析。扩展恢复后通过 `legacyWeapon`、`legacySupplies` 解析，扩展备弹数量不会被强制改成八发。`PatrolSupplies.loadout`／`preference` 只作为旧调用的兼容入口，底层仍是一份配装分配。

`LoadoutProvider` 说明实物如何使用：`accepts`、结合背包的 `usable`、`ranged`、`range`、弹药 `ItemSpec`、`magazineSize`、按组件计数的 `roundsLoaded`／`loadedAmmunition`、`cycleTicks` 及 `suggestedAmount`。添加武器时据此预填可编辑的补给条目，建议值不控制后续领取。枪械模块分别注册这些参数及真正执行的 `WeaponAdapter`／`WeaponSession`，此处不提供假枪械逻辑。`profile.hasRanged()` 查询条目，不要求装备到手或当前有弹。

不安装 RTS 也可打开聚落书的「配装」页。左栏为可翻页配装列表和命名操作，右栏为所选配装概要及紧凑条目行；窄窗口上下排列，条目表可横向滚动。统一「＋ 添加」菜单提供武器、武器型号、补给、观察器材和四个护甲栏位。每条显示图标、名称、简短缺额与目标量；只有补给显示可编辑目标、补给阈值和一个保存按钮。排序、移除和更换使用稳定条目 UUID。悬停状态区分已分配居民缺件与仓库缺件。库存预览遵守登记和预留规则，不产生新预留。

「分配居民…」打开与聚落书相同风格的可翻页列表，显示姓名、当前工作／状态和配装选择。选择配装或「无配装」立即生效；每次请求重查管理权、居民归属、预期原分配和目标配装修订号。冲突显示提示，行内继续显示服务端确认值。未加载居民可分配；关闭窗口不撤销已接受的修改。删除配装清除分配。添加／更换弹窗在打开时捕获配装、条目 UUID 和修订号。

配装账本在组件解码前递归迁移精确组件与附魔限定，因此已消失的附魔编码不会阻止普通物品／标签加载。枪型和弹药组件身份保留；TACZ 旧手持配件条件移除而 GunId 保留。转换后立即保存为版本 4；Core 通用 ItemSpec 组件支持不变。服务端拒绝旧 exact、enchantments、held_weapon 动作。巡逻无配装策略和有限领取生命周期保留既有契约。

### 有限领取与交战选械

已分配的居民通过 `PatrolSupplies`／`PatrolSupplyNode` 各自领取缺少的物品。普通居民、绘制巡逻员可领取；守卫仍使用原有命令授权。其他手动命令、失败等待及普通选区保留不会触发维护绕行。领取让位于战斗、恐惧及撤退，实际走到 32 格内登记仓库，在到达时重查权限、预留、组件、容量与现货。每程上限 200 tick，缺货和满包有限退避重试；新命令或配装修订使旧领取失效。补给严格在携带量低于阈值时开始，即使部分领取后超过阈值，也持续补至目标。已装填弹药按真实组件只计一次，不生成装备或修复耐久。

`Weapons.select(worker, target, current)` 同时考虑真实主手借用和有序配装武器。有视线时按目标距离选择可用远程武器，敌人靠近或缺弹时改用近战；原有可用随身工具／装备仍可作为后备。先关闭旧会话，再开启新会话。`StrikeNode` 和 RTS `AttackNode` 使用同一规则及目标相关的接近距离；原生会话继续检查敌意或显式目标授权、视线、射程、弹药与生命周期，受重伤时恐惧仍优先。

Core `Equipment` 管理四个护甲栏位并拒绝不兼容物品。需求标记 `automaticSupply=false` 让配装走居民有限领取，避免普通工具配送另行索取。玩家给予的其他护甲不会被覆盖，占用栏位会显示；无可用武器提供者或护甲不适配时显示不可用。副手／盾牌暂缓，因为既有装备所有权只支持人形护甲。原生主手会话及配装领取目前服务 `ResidentEntity`，其他 ResidentKind 保留所属扩展的 ToolUse／裸手执行。

巡逻不再声明武器工具包或工具列表编辑器，移除可选武器用的 `KitRules.defaultTool`／`defaultTools` 和 `CoreSettings.defaultTool`，不再注入弓弩许可。战斗领取直接依据配装物资，独立于已保存的职业工具许可。非战斗职业的白名单和自动工具行为不变。绘制路线的守护工作本身无武器工具门槛，战斗仍要求策略许可和可用装备。原有玩家武器继续以实物保留。独立的 `KitRules.supplyPolicy` 仍负责普通配送的生命周期协调。

## 哨位、共享目击与巡逻支援

原版模块的巡逻职业拥有 `folkways:sentry` 方框区域，以及殖民地之书中的「哨位」页面。
用现有区域工具画出小区域，再在页面中派驻或撤离居民。区域绘制修饰键、RTS 选择快捷键和直接命令
保持原有含义。居民必须拥有 `hasRanged()` 为真的配装才能驻守；派驻不要求已携带弹药。
目前只有原生居民支持武器操作，其他居民种类会显示明确的不支持原因，等待其所属集成实现对应操作。

容量为 `min(安全站位数, max(1, floor(水平面积 / 4)))`。叠加高度不会增加水平面积。区域可以标记脚下
支撑方块或站立格，居民在该列中选择有支撑且头顶畅通的位置，不会追出哨位。四格地板容纳一人；
5×5 地板在站位足够时容纳六人。`folkways:sentry_posts` 保存 `assignments` 列表，每项包含
`resident` 和 `zone` UUID。未加载居民保留派驻记录；居民离开殖民地或区域被移除时清理记录。
方案失效或容量减少会暂停驻守并显示原因，不会暗中改写玩家的派驻安排。

`SpottedTargets.of(colony)` 保存有上限的临时目击记录：目标 UUID、实体编号、维度、目击位置和时刻。
视野没有朝向限制；基础值与警觉专长参与后文“动态成对视野”的高度、亮度与实物倍率计算。
目击要求真实视线，并沿用 `Threats.hostile` 的敌意判断；防卫居民会报告所有看见的敌人。
只有真实目击才能更新位置和时刻。目标死亡、卸载、记录过期或失去敌意都会使记录失效；中立生物的
愤怒状态还会针对实际开火居民重新判断。间接射击也会拒绝已偏离目击位置超过两格的目标。
服务不会加载缺失区块，目击记录不会存档。

哨兵使用可用的远程方案手持武器，混合近战与远程的方案仍可正常驻守，不再因区域包含而借用
固定武器；独立实体炮位使用自己的人员槽位。有效射程来自 `LoadoutProvider`。自身视野内射击受武器射程限制；共享目击允许超出自身视野
半径开火。直射仍要求开火时有自身视线，且射线上没有友方或同殖民地居民。
`LoadoutProvider.indirect(stack)` 声明间接武器，其适配器必须实现
`WeaponSession.spottedTarget(target, observedPosition, authorized)`，并在每次真正发射前检查实时授权。
原生弓弩支持目击授权，同时保留直射弹道和真实弹药消耗。换目标会取消旧射击，每次间接射击绑定不可变
目击快照，不会从视野外实体暗中获得新坐标。健康哨兵交战优先级为 2.5，平时驻守为 1.5；恐惧、
补给与直接指挥仍按原有优先级生效，重伤居民仍可逃离危险。

普通路线巡逻改为按视野发现敌人，取消原先固定十二格发现限制。具备间接武器的防卫者可以自行取得不可见的共享目标。直射远程武器可通过
`longRange(stack)` 明确启用共享索敌，但仍要求自身当前视线与有效射程，不增加追击距离。
原生武器默认不启用 `longRange`。两种声明都要求武器会话执行实时目击授权检查。哨兵看见敌人超出射程，或敌人进入哨位近战距离时，会呼叫附近健康、已武装且
正在执行路线的巡逻居民。按距离选择支援者，限制每个目标的支援人数与支援时长。已有战斗、已派驻、
直接命令、选择保留或失败等待中的居民不会响应。支援使用现有执行器的临时战斗工作，不会完成巡逻
观察节点、重建轮次或替换路线。目标消失、记录过期、超时或接到直接指挥会撤销支援，随后继续未完成
路线。RTS GUARD 原有的十二格岗位与战斗站位约束，以及仅防御语义保持不变。

`WeaponStations.register(id, finder)` 是原版模块的固定武器扩展入口。发现器返回区域内固定武器的稳定
`Station` 实例。固定武器声明 `WorldPos`、有效射程、是否间接射击、弹药 `ItemSpec`、可选冷却与有效性
检查，以及同步 `operate` 和 `release` 回调。原版管理独占租约，每次成功操作消耗一份真实匹配弹药；
集成不得重复扣除这份弹药。操作返回失败时不消耗弹药。默认发射点位于固定武器格上方 1.5 格，集成可提供实际炮口位置。
固定武器的射程、地形和友方射线检查均从该点计算，也会保护站在炮口前方的操作员。原版没有具体固定武器或免费弹药。离开哨位、
被其他工作抢占、方案失效、固定武器消失、死亡、卸载、退籍、区域移除或殖民地关闭都会释放租约。
GameTest 中的固定武器仅为测试替身。

区域卡显示驻守居民、拒绝的居民及原因、视野总上限和当前目标。悬停或选中哨位时显示服务器提供的最大可能视野
圆环，包含居民警觉加成。派驻页面显示未加载、已满、无安全站位、直接指挥、缺少武器或弹药、射线被挡
和固定武器故障等状态。写入操作经过书本当前管理权限检查，再在服务器验证区域归属与居民成员身份。
巡逻职业目前没有 Ponder 教程文件夹，因此没有单独注册哨位课程。

## 按装备配置编制与自主巡逻队

当前人员获取、迁移与面板入口以“按装备配置编制与自主巡逻队”章节为准；下文旧批次的
槽位／固定居民审计与工程结果是历史记录，不再定义当前配置流程。

Vanilla 的 `PatrolStaffing` 使用账本 `folkways:patrol_staffing`。每个哨区和巡逻路线在自己的
配置面板设置**允许的配装**（多选弹窗列出聚落全部配装）与一个总**人数**。允许集合为空时不选人，
人数为零时停用，不会恢复旧单人巡逻或手动派驻。哨区仍要求远程装备和安全站位容量，不合条件的选择
会显示缺员原因；路线接受任意允许的已分配配装。指定居民与独立人员编制书页已删除；路线面板保留**重试路线**。

每台明确纳入的武器站自动需要一名有任意配装且未在别处服役的居民，近战或仅补给配装也符合条件。
仍须逐台纳入，绑定精确原生实体 UUID。**哨位**总览显示武器身份、操作员和运行故障，并可在卸载时
**撤出武器站**。没有逐炮配装或岗位配置；`StationPost` 仅是现有执行器的临时几何适配器，不是存档岗位。

调配先在所有目标中保留现任成员，再按 UUID 顺序补武器站，然后按 UUID 顺序补哨区／路线；候选居民
也按 UUID 排序。新炮位不会抢走有效哨兵或巡逻员，一人只能服务一个目标。卸载保留名额 200 刻。
直接指挥、选择保留和失败待命暂停有效职责，不替换手动命令；实时职责检查撤销武器会话和武器站租约。
死亡、退籍、职业许可丢失或配装不再匹配会释放成员；容量下降和远程能力丢失仍作为可见暂停。
缺弹、座位占用、射线受阻和无法接近等运行故障与缺员分开显示。

新存档目标行保存 `allowed` 配装 UUID、`count` 及带稳定身份／可选现任成员的内部 `positions`。
内部位置维持站位与延迟职责身份，玩家不逐项编辑。缩编先重新检查实时资格，优先删除空位并保留
有效现任成员；站位索引变化时更新职责身份，撤销旧工作。武器站只从纳入记录派生需求，运行中现任操作员
另存为 `operators`。旧 `slots` 加载时转换为配装并集与槽位总数，丢弃 `pin`，有效 `member` 可以保留。
旧武器站槽位与配装岗位配置丢弃，已纳入武器自动补员。更早的 `sentry_posts.assignments` 转成聚合
允许配装与人数后清空。已删除配装的 UUID 保留为可见缺员，直到选择器替换。
配装页兼容 API `shortageFor(profile)` 表示该配装可补的总缺额，多个允许配装共享缺额，不能跨配装相加。

每次编辑都重新验证持书管理权限、聚落、当前目标、维度和配置修订。弹窗捕获原目标，旧弹窗不能改动
后来选中的区域。此批不改 RTS 快捷键、修饰键、选区、命令协议、配装编辑页或居民分配配装流程。

`plugins.combat.group.GroupDeployment` 提供队形几何计算，`GroupRoute`
提供逻辑行进锚点、有界路径与站位规划、安全相连站位、成员相对偏移及附近重整锚点搜索。
调用方传入自己的目的地验证器。RTS 的 `Deployment`、`PointRoute` 通过适配器继续使用
原有命令验证，RTS 保留命令句柄、必经点生命周期、控制所有权及 `folkways:unit_groups` 存档格式。
`GroupMotion` 提供自主集合、宽松队形行进、交战暂停与重整，不持有寻路器；
`PatrolTeams` 在 Vanilla 通过同一个工作执行器提供普通自主工作。

有编制的路线即使缺员也由已补足成员集合、结队巡逻，在每站警戒并于两端折返。
一人发现有效敌人时全队暂停；每人仍遵守原有敌意、视线、弹药与武器会话检查。
交战和哨位求援保留未完成站点；结束后回到原队形并稳定集合 20 刻再继续。
恐惧和有限补给可以借用同一个执行器，直接命令、选择保留与失败等待继续优先。
求援将队伍与原有单人响应者按距离统一排序，以 UUID 打破平局。队伍距离取最近已补足成员，
且全员必须在求援半径内。整支队伍作为一个响应单位，沿用现有求援时限，
失去目标或到期后回到原路线。
每次等待掉队成员最多 200 刻并允许两次重新规划；恢复耗尽或有效行进达到 1200 步后
显示路线受阻并释放自主移动工作，不会跳过未完成站点；编辑器提供重试路线，成员变化也会允许恢复。

### SBW 居民手持枪械姿势

SBW 0.8.9.2 为 `GunGeoItem` 注册客户端扩展，`getArmPose` 委托枪械自己的姿势方法。
普通枪械的 `PoseTool.pose` 在瞄准时返回 `BOW_AND_ARROW`，装填、蓄力或着地冲刺时
返回 `CROSSBOW_CHARGE`，部分枪械子类覆盖该方法。Minecraft 玩家渲染器会查询这个
扩展；居民皮肤渲染器没有查询，Warfare 也没有注册 `ResidentWeaponPoses` 提供器，
导致真实持枪的居民仍使用普通物品手臂姿势。

`WarfareClient` 现在仅在客户端注册提供器，通过既有适配器接受物品后查询原生扩展。
重置的人形模型根据原生姿势、惯用手、头部瞄准和动画相位计算双臂旋转，再交给已有
皮肤／Geo 姿势接口；皮肤渲染器将旋转复制到袖子。没有在渲染器增加枪名或手臂角度表，
未来被适配器列表接受的枪械沿用同一桥接。

状态来源与 TACZ 一致：服务端 `claimWeaponHand` 在战斗期间借出真实主手枪械，
`releaseWeaponHand` 清空并归还，通过装备同步到客户端。客户端不读取服务端本地会话
字段，也不自行授权瞄准、目标或射击。举枪不能证明当前射击通过了视线、有限弹药和
友军通道检查。

独立 `rts_design_auditor` 已批准本次静态设计，无阻断项。接受范围保留现有输入与修饰键
归属、选择、命令、服务端权限、可见失败状态及会话撤销。验收夹具覆盖原生双臂旋转、
袖子、接受与拒绝的物品、真实哨位交战及主手释放；工程结果与实机截图作为独立证据。
Geo／女仆／薄臂外观组合、多客户端及冲刺／装填／骑乘／游泳的完整视觉组合继续延期，
本次不扩展武器支持或 RTS 路线图。

### 原生范围灭火与水带领取

可选消防桥接针对 FireFighting Additions 0.2.5-beta-fix2。检查固定版本 jar 确认，便携灭火器使用
`FireExtinguisherSprayEffects.applyBlockEffects`：半角 14 度、射程四格的锥体，包含方块半径容差、
最多 128 个按距离排序的采样及原生视线检查。水带使用
`HandheldNozzleSprayEffects.applyBlockEffects`：配置中的锥形或扇形喷流和射程、8–28 条射线，
以及 0.75 格采样步长。居民桥接直接调用这些原生方块效果路径，保留附带方块效果和消防栓所有者归属，
不再仅处理分配给居民的单个火格。仍仅支持水；设备、所有权、执照、区块加载与绑定检查由服务器执行。

桥接读取附属模组的原生消耗常量。居民灭火器每次脉冲最多消耗 5 mB，在两刻消耗间隔内不能重复；
水带每次脉冲最多消耗 10 mB，同一刻不能重复。原生容器允许用尽最后不足一次标准消耗量的水。
关闭并重新开启会话不会重置间隔限制。范围内的命中共用该次脉冲的消耗，包括发起灭火的保护区之外的火，
附带灭火不会创建额外认领。目标选择仍来自已启用保护区的有界巡查。付费脉冲之后，仅复查已知事故，
移除已熄灭的巡查记录、关闭受影响的响应并释放精确匹配的认领。其他居民已分配的任务无害完成，
不再重复喷射；后续复燃作为新的工作被巡查发现。

水带工作在走向柜体、短暂领取交互、携带连接的水带行走及喷射之间保留同一个普通响应。
初始站位是柜体相邻的安全格。到柜前重新检查可用性与权限后才绑定，挥臂并显示原生控制器。
随后同一会话使用居民身体的移动抽象走到安全喷射站位，持续遵守原生最大绑定距离及现有取消与清理规则。
喷射站位为移动抽象的到达容差留出余量。`OnFoot` 在前往或执行灭火时跳过施工区域内的重定位，
确保两段路程都通过导航行走、不传送。这项窄范围移动修正是消防和损管之外唯一的实现改动。

原生水带渲染器在首次喷射之前就使用移动居民的当前锚点。这些数据包只负责表现，不授权世界效果。
释放会立即解绑，已经喷出的视觉尾迹可独立播放完毕。

独立 `rts_design_auditor` 已批准本批次的静态设计。现有输入与修饰键归属、手动控制优先级和事故并发上限保持不变。

## 动态成对视野

`SpottedTargets.sight(observer, target)` 返回指定观察者与目标之间的发现距离。
令 `h = min(max(观察者眼高 - 目标眼高, 0), sightHeightLimit)`，警觉加成为 `v`，
目标有效亮度为 `L`，实物望远镜倍率为 `m`，服务端计算：

```text
dark = min(darkSightLightLevel, fullSightLightLevel - 1)
light = darkSightMultiplier + (1 - darkSightMultiplier) * clamp((L - dark) / (fullSightLightLevel - dark), 0, 1)
radius = clamp((defenderSightRadius + v + sightHeightPerBlock * h) * light * m,
               min(minimumSightRadius, maximumSightRadius), maximumSightRadius)
```

观察者有夜视、目标着火／Glowing，或目标类型属于 `folkways:luminous_targets` 时，
`light = 1`。默认标签含烈焰人、发光鱿鱼、岩浆怪，数据包可扩展。
`m` 默认是 1；只有已分配 SUPPLY 条目匹配背包实际持有的认可观察物品，才使用
`observationSightMultiplier`，不按数量叠加。数量、缺货和档案 revision 继续复用既有补给系统。

目标位置仅查询一次原版 `getMaxLocalRawBrightness`，包含方块／天空光与
`getSkyDarken()`；后者已考虑时间、雨和雷雨。不重复扣天气系数，不扫描地形高度，不增加
射线。眼高直接与目标眼睛比较，城墙／塔楼对低处目标有优势；仰视既不加成也不额外惩罚，
避免普通上坡遭遇意外失明。高度增幅封顶，距离仍按三维计算。

以下参数均属于服务端 `sentries`：

| 配置                         | 默认 | 允许范围 | 含义                           |
| ---------------------------- | ---- | -------- | ------------------------------ |
| `defenderSightRadius`        | 32   | 1–128    | 警觉与情境因素之前的基准       |
| `sightHeightPerBlock`        | 1.5  | 0–8      | 每格正眼高差增加的距离         |
| `sightHeightLimit`           | 16   | 0–64     | 最多计算的高度差               |
| `darkSightMultiplier`        | 0.25 | 0–1      | 目标有效亮度为零时的距离系数   |
| `darkSightLightLevel`        | 4    | 0–14     | 不高于此有效亮度时使用黑暗倍率 |
| `fullSightLightLevel`        | 12   | 1–15     | 恢复完整距离所需有效亮度       |
| `observationSightMultiplier` | 2    | 1–4      | 实物观察倍率；1 为关闭放大     |
| `minimumSightRadius`         | 3    | 1–16     | 近距下限，仍要求视线           |
| `maximumSightRadius`         | 128  | 1–128    | 发现与粗筛的共同硬上限         |

默认同高明亮目标在无技能时为 32 格，真实望远镜为 64 格。有效亮度 0–4 为 8 格，包含
原版夜间天空亮度 4；亮度 8 为 20 格，亮度至少 12 时为 32 格。八格眼高差在光照与望远镜之前
增加 12 格，因此白天城墙为 44 格，携望远镜为 88 格；高度最多增加 24 格。
若下限配置高于上限，以上限为准。近距也必须满足 `hasLineOfSight`、同维度与目标区块已加载。
不会增加武器射程，也不授予攻击非敌对目标的权限。

移除原仅观察者参数的 `sight(observer)` API，单独提供 `maximumSight(observer)` 用于扫描／UI：
取最大高度收益、亮度系数 1、当前技能与实物倍率，再经过相同 clamp。高度非负、亮度系数不大于 1，
保证此上界覆盖所有成对结果。一次观察扫描只读取一次观察者基础值／技能／实物倍率，
先按球形上界排除过远候选，再对剩余候选至多查询一次亮度并执行既有 LOS；随后直接记下
已校验目击，不重复调用 `report`。
记录前保留服务端线程、居民归属与 holding 门槛，公开 `report` 仍独立校验。
不做跨 tick 缓存，照明、效果、物品和档案变化影响下一次判定；不加载缺失区块。

哨位圆环和四语言提示均明确为**最大可能视野**；无人／未加载回退使用全局硬上限并保留
相同说明，圈内不保证发现。巡逻、哨兵、Warfare／TACZ 观察会话及火炮前观统一使用成对判定，
可选枪械集成不增加独立视野公式。真实报告仍遵循原有 TTL／敌对关系／位移规则，
不因其后照明变化追溯删除。

删除原 `observationSightBonus` 字段、访问器和配置声明；不把旧固定加值自动换算为倍率。
保留 `defenderSightRadius` 作为基准；档案／存档 schema 与实物望远镜补给无需迁移。

## 32 格基准校准

`defenderSightRadius` 的新默认是 **32**。近距下限 3、总上限 128、高度每格 1.5／最多 16 格、
黑暗倍率 0.25、完整亮度阈值 12、实物望远镜倍率 2 均保持不变。无警觉技能时，白天平地 32 格、
八格眼高优势 44 格，该城墙上携望远镜 88 格（平地望远镜 64 格）。

需额外增加一个低光阈值：旧插值在原版夜间有效亮度 4 时会得到 16 格，而不是期望的约 8 格。
`darkSightLightLevel=4` 让有效亮度 0–4 使用原来的 0.25 倍率；亮度 8 得到 20，亮度至少 12 时
得到 32。允许范围 0–14，实际阈值规范化为小于 `fullSightLightLevel`，即使管理员配置两阈值
重叠也不会除零。设为 0 可恢复前一版亮度插值。旧服务器配置的基准值（包括 12 或 64）原样保留，
不强行迁移存档／配置到 32。

### 当前损管契约：保守规划喷位、普通到达

用户替换了 `10755cd22` 的精确到达方案：在挑选原生喷射站位时保证普通到达容差内的射程与视线，
到达后直接调用原生效果，不再追加集成层的距离、锥形或射线预检。
`ExtinguisherAdapter.range()` 引用 `FireExtinguisherSprayEffects.RANGE`；水带按实际锥形／扁平
喷嘴调用附加组件的 `rangeFor`，不复制其射程数字。

`SprayFootings` 把站位中心眼距限制为原生射程减 `Reach.IN_THE_CELL`（0.9），再减 0.05 格。
在应用这段水平余量前，还检查普通一格高度容差内最远的眼位。由三角不等式可覆盖整个允许到达圆盘
与高度区间，而不只保证格子中心。水带站位对原生 32 格连接长度同样预留该范围。

遮挡检查使用包住整个允许眼位盒与火心的 AABB；所有可能眼位至火心的线段都包含于这个凸盒中。
与盒相交的任何方块碰撞形状都会拒绝该站位，使用与原生 collider 射线相同的空碰撞上下文；
整个体积中的未加载区块同样拒绝，不加载新地形。它比检查若干射线更保守，也覆盖采样射线之间的
墙角和细障碍。水带包络向下扩展原生起点的 0.18 格偏移，并要求最近可能眼位距目标至少 0.75 格，
确保沿目标方向前移 0.75 格仍在包络内。这两个偏移原本就属于原生起点适配，没有改动原生效果。

`DamageControlPresence` 固定产生该组站位的具体方法，`ExtinguishNode` 只打开该方法，

所有者、居民和 32 格距离等权威检查。徒手扑火直接删除火格，没有原生喷射采样器，因此保留其自身
射程／视线守卫。

### 水带远射程：原生服务端采样与近栓站位优先

本次后续替换水带候选站位的选择顺序，沿用上文的普通到达和真实付费喷射契约。
核对 `blockwright.toml` 锁定的 `createfirefightingadd-0.2.5-beta-fix2.jar` 实际类后，确认有两条不同路径：

- 配置加载时，`Config.clampToPhysics` 把各喷嘴有效射程设为
  `min(配置值, floor(速度 / (1 - 阻力保留率)))`；
  `HandheldNozzleSprayEffects.rangeFor` 返回这个有效值。默认锥形 50 格、扁平 35 格，
  居民通过 `NativeSprayBridge` 读取，不另加 4 格或 32 格喷射上限。
  32 格消防栓连接距离仍是单独的权威校验。灭火器仍读取原生 `FireExtinguisherSprayEffects.RANGE`，即 4 格。
- 服务端 `HandheldNozzleSprayEffects.applyBlockEffects` 调用
  `SprayEffectSampler.traceRays`：归一化直线碰撞射线，不检测流体，使用空碰撞上下文，
  每 0.75 格采样，最多 512 格、4,096 个去重方块。两种原生喷头都先采样瞄准中心线，
  再采样旋转散射。带速度、重力和阻力的弧线属于客户端抛射物显示；这个版本并不沿这些弧线执行服务端方块灭火。
  因此继续使用连续直线视线包络；另造抛物线预测器反而与原生实际效果不符。
  视觉水滴的弧线不能越过阻挡原生中心线的墙并在服务端灭火。

### 普通灭火工作与真实喷射后的兜底

也使用这一工种默认值。居民和殖民地模板的已保存显式设置优先，包括 `THIRD` 和关闭工种；其他工种
默认值不变。

节点按水带、灭火器、徒手顺序选择第一个可用方法，并固定站位。水带还捕获准确柜子、消防栓标识、

不会在节点内部临时换方法或换柜。

待执行计划不占火点或实际响应额度；多名居民可持有同一地址的候选工作，由 `Incidents` 限制每个火点
与居民各一份实际认领，并遵守 `damageControlConcurrency`。前面的居民忙于其他工作时，后面的空闲
居民仍可响应。保留每刻共享选点额度、最多 128 个已知地址的轮换候选批、居民重试间隔和跨维度轮换
的有界扫描。

到达计划喷位后，节点调用所选会话一次。只有明确的 `performed()` 证明真实付费原生喷射已朝目标发出，
